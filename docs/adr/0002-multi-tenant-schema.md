# ADR-0002 SaaS 多租户预留：全业务表 tenant_id

- 状态：已采纳
- 日期：2026-10-29
- 决策者：用户（「要预留 SaaS」）

## 背景

当前为纯私有化局域网单客户部署。用户要求预留 SaaS 多租户能力，但近期不做云端运营。若等 SaaS 化时再补租户隔离，存量数据迁移与全链路改造代价极大。

## 决策

1. 服务端**全部业务表**加 `tenant_id TEXT NOT NULL DEFAULT 'default'` 列；私有化部署恒为 `'default'`。
2. 所有读写 SQL 必经租户谓词：`WHERE tenant_id = ?`；租户上下文从请求解析（当前实现：请求头 `X-Tenant-Id`，缺省 `'default'`；SaaS 化时改由身份令牌签发）。
3. **单代码线不变**：不引入 SaaS/私有化代码分叉，差异仅由租户配置承载。
4. 唯一索引全部升级为 `(tenant_id, 原键)` 复合形式。
5. 迁移策略：建表即带列（当前库无生产数据，直接重建）；已有数据的现场执行 `ALTER TABLE ADD COLUMN tenant_id DEFAULT 'default'`。

## 备选方案

- A. 每租户独立数据库：隔离最强但私有化部署运维复杂、且当前单客户无收益，否决。
- B. 不加列、SaaS 化时再迁移：迁移窗口长、风险高，否决。
- C. Schema 级隔离（每租户一个 SQLite 文件）：备份/迁移粒度好，但连接管理与跨租户统计复杂，留作未来选项。

## 后果

- 正面：SaaS 化时无需数据迁移；租户隔离从第一天就是强制路径而非补丁。
- 代价：所有新 SQL 必须带租户谓词（代码评审检查项）；`'default'` 租户名成为保留字。
- 验证：跨租户读写隔离测试（A 租户数据对 B 租户不可见、不可改）。
